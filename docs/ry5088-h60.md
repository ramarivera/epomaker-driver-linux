# RY5088 H60 migration

Target: **H60, internal ID 3662, USB 3151:5029**. Other keyboards use the same
VID/PID; the firmware identity must match before configuration commands are sent.
The installer catalog calls this model `ry5088_hf_k1_1m_8k`.

The CLI supports keymaps, four profiles with four normal submodes each, both OS
Fn maps, macros, OS options, main lighting, five custom pictures, magnetic reads,
actuation/rapid-trigger settings, DKS/mod-tap/toggle modes and snap pairing/removal.
Magnetic writes compare complete affected state on readback. Debounce, sleep,
firmware updates remain gated; [schema 7 recovery](he-recovery.md) is implemented.

## Source evidence

The baseline archives are identified in [source-releases.json](source-releases.json).
The name-keyed finder loads macOS `00bc96cb.js` and Windows `82c2850d.js`.
These import the modern command base `623d2d52.js` / `17dc9c62.js`, respectively.
Both declare matching 512-byte default normal, Fn and Fn-Mac matrices without
child method overrides. See [model inventory](model-inventory.md) for the broader
RY5088 crosswalk. Private installer code is not redistributed.

The catalog declares four normal profiles and one Fn layer for each OS. The
modern base stores four normal submodes per profile: profile index and submode
are separate packet fields. A profile index must not be multiplied by four.
The USB catalog filter uses usage page `ffff`, usage `2`, interface `2` and
report rate `8000`; discovery must additionally inspect the actual HID report
descriptor rather than treating that filter as proof of report shape.

The `S` lighting layout provides 21 main effects and five custom picture banks,
with no explicit off effect or side lighting. Custom pictures hold 126 RGB slots.
H60 has no catalog debounce or sleep setting and declares that its switches are
not replaceable. Shared superclass methods do not establish public support for
these absent controls.

## Magnetic bounds

Unlike HE60 Lite, H60 has no `travelSetting` override. The UI therefore uses
firmware-dependent default steps and rapid-trigger bounds:

| USB firmware | Step | Travel/lift | Rapid press/lift | Dead zone |
| --- | --- | --- | --- | --- |
| Nonzero, below `0300` | 0.1 mm | 0.1–4 mm | 0.1–2.5 mm | 0–4 mm |
| `0300`–`04ff` | 0.01 mm | 0.1–3.3 mm | 0.01–2 mm | 0–1 mm |
| `0500` or later | 0.005 mm | 0.1–3.3 mm | 0.005–2 mm | 0–1 mm |

A missing/zero version uses 0.1 mm steps, a 3.3 mm travel maximum, a 2.5 mm
rapid-trigger maximum and a 4 mm dead-zone maximum, following the UI's different
truthiness checks. Top dead zone requires firmware at least `0400`, ranges from
0 to 1 mm and uses the current default step. Lift is bounded by maximum travel
minus the resulting bottom dead zone. Existing omitted values must be preserved;
enabling rapid trigger must validate both resulting rapid thresholds.

Evidence in private prettified main bundles:

- macOS 107677–107700 / Windows 106589 onward: firmware-dependent default step.
- macOS 107169–107182 / Windows 106081 onward: maximum travel and version check.
- Both main bundles at 9918: switch travel maximum is 3.3 mm.
- macOS 107710–107919 / Windows corresponding section 106622 onward: travel,
  rapid-trigger, bottom/top dead-zone limits and steps.
- macOS 105586 / Windows 104498: main controller version selection.
- macOS 57764 and 57862–57879: EPOMAKER branding and custom-driver list; EPOMAKER
  is outside that list, so custom-brand rapid-trigger overrides do not apply.

Wire travel scaling remains the modern base's version-dependent multiplier:
10 below `0300`, 100 below `0500`, and 200 thereafter. The distinct
`7bb580fe.js` precision-extension superclass is not in H60's inheritance chain.
Dynamic keystrokes use four actions, a 0.5–2.5 mm threshold in 0.01 mm steps,
and four trigger-mode bytes. Mod-tap stores time in 10 ms units; the UI permits
10–1000 ms and truncates fractional units. Snap uses reciprocal physical-key
slots and restores ordinary bindings when a pair is removed, as described in
[HE60 Lite research](he60-lite-research.md).

## Remaining work

Hardware behavior, persistence and reconnects require physical comparison.
Firmware updates and graphical controls remain migration gaps. No amount of simulated test coverage establishes
hardware verification or an overall feature-parity percentage.

[Timed USB calibration](calibration.md) now provides start/stop sequencing and raw
telemetry for these models. Physical calibration results and recovery behavior remain unverified.

## Schema 7 recovery

[Magnetic backup and restore](he-recovery.md) now covers all migrated
configuration domains, including inactive magnetic fields and all macro slots.
It requires USB and exact firmware versions. Physical hardware verification
and persistent sensor calibration recovery remain outstanding.
