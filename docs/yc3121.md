# YC3121 / CommonKbYc500

The CLI has partial direct-USB support for RT100 (internal ID 1379) and
Dynatab75X-UK (1723). Both have three normal profiles. Key remapping, raw and
semantic matrix reads, profile selection, sleep timers, debounce and automatic
OS selection, macro storage/bindings and main lighting are implemented with write readback. Neither has been tested on
physical hardware. The GUI still supports Glyph only.

Their USB filter is `3151:4015`, usage page `ffff`, usage `0002`, interface 2 in
both installers. Linux additionally requires a report-ID-zero 64-byte feature
collection. A shared product ID only selects the protocol implementation;
configuration remains gated on the internal model ID. Bluetooth and receiver
routing for this family have not been enabled.

## Evidence

The sources are the two 3.2.22 installers recorded in
[source-releases.json](source-releases.json). The following module pairs are
byte-identical after replacing imported chunk filenames:

| Role | macOS chunk | Windows chunk |
| --- | --- | --- |
| CommonKbYc500 | `7b0fe1d1.js` | `0175ea1e.js` |
| Older keyboard parent | `ef0a2b57.js` | `17f7eda9.js` |
| RT100 model | `54eeccef.js` | `9f695dc5.js` |
| Dynatab75X-UK model | `3f129dcd.js` | `b3a53363.js` |

All four pairs were compared in full. Model loaders and catalog fields
establish inheritance and capabilities; model matrices have not yet been
published in this repository. Vendor JavaScript stays outside the public repo.

The older family's class name alone does not establish support. HE75 Mag
internal ID 1955 also inherits this base, but magnetic profiles use
`profile * 4 + sublayer` addressing and require additional migration. The
YC3121-named ID 3727 inherits the newer keyboard base instead.

## Commands and offsets

Offsets below are in the 64-byte command payload before the USB report-ID byte.
These commands use the complement checksum at byte 7, covering bytes 0–6.
Queries returning keymap pages return 64 raw data bytes without an opcode prefix.

| Operation | Request | Relevant fields / response |
| --- | --- | --- |
| Internal ID | `8f` | Common transport: uint32 LE at reply bytes 1–4 |
| USB firmware version | `80` | uint16 LE at reply bytes 1–2 |
| Read active profile | `85` | reply byte 1 |
| Select profile | `05` | byte 1, zero-based 0–2 |
| Read normal matrix | `89` | byte 1 profile, byte 2 page 0–7 |
| Set one normal key | `13` | byte 1 profile, byte 2 slot 0–127; four action bytes at 8–11 |
| Read debounce | `91` | reply byte 2 |
| Set debounce | `11` | byte 1 zero, byte 2 value |
| Read sleep timers | `92` | four uint16 LE values at reply offsets 1, 3, 5, 7 |
| Set sleep timers | `12` | four uint16 LE values at command offsets 8, 10, 12, 14 |
| Read macro | `8b` | byte 1 slot 0–255, byte 2 page 0–3; 64 raw reply bytes |
| Write macro | `16` | byte 1 slot, byte 2 chunk 0–4, byte 3 length 56, byte 4 final commit; data at byte 8 |
| Read custom picture | `8c` | byte 1 bank 0, byte 2 page 0–5; 64 raw reply bytes |
| Write custom picture | `0c` | byte 1 bank 0, bytes 2–3 `128,1`, byte 4 chunk 0–6, data at byte 8; seven 56-byte chunks |
| Read automatic OS selection | `97` | reply byte 1 equals 1 when enabled |
| Set automatic OS selection | `17` | byte 1: 0 or 1 |

The `8f` version and boot-state fields used by newer models are not assumed to
apply here. Identification requires an explicit `80` version reply; zero and
`ffff` are rejected. Status reports `is_boot: null` because there is no migrated
boot-state detector. Firmware operations remain unavailable.

Timer order is Bluetooth sleep, receiver sleep, Bluetooth deep sleep, receiver
deep sleep. Both models expose all four: ordinary timers 60–3600 seconds, deep
timers 600–3600 seconds. Debounce is encoded as one byte; the catalog's `deBounce:
10` enables the vendor control and is not treated as a proven maximum.

The vendor UI uses `setKeyConfigSimple` for a single selected key (macOS
main-bundle lines 116010–116016 and 117039–117045). The vendor bulk writer declares 504 bytes and emits nine 56-byte chunks using
`09`. Reads expose 512 bytes. The independent Python `write_matrix` method
instead compares all 128 slots, sends `13` only for changed slots, then compares
the full readback. This retains unknown slot bytes and permits editing slots
126–127 without truncating them. A failure can leave earlier writes applied;
there is no claimed rollback. Each operation uses the transport transaction
lock, and writes retain the parent's 500 ms settling delay.

## Use

```sh
epomaker discover
epomaker --device /dev/hidrawN status
epomaker --device /dev/hidrawN matrix --profile 0 --decoded
epomaker --device /dev/hidrawN bind-key 9 a --profile 1
epomaker --device /dev/hidrawN profile 1
epomaker --device /dev/hidrawN sleep 120 240 1800 3600
epomaker --device /dev/hidrawN debounce 10
epomaker --device /dev/hidrawN auto-os on
```

Slot numbers are physical matrix positions, not keycodes. Read the current map
before choosing a slot. `key` also accepts a four-byte raw action. Fn and
nonzero OS selectors are rejected until their older-family semantics are
migrated.

## Macros

The inherited reader (`ef0a2b57.js` / `17f7eda9.js`, `getMacro`) reads four
64-byte pages using `[8b, slot, page]`. The CommonKbYc500 override (`7b0fe1d1.js`
/ `0175ea1e.js`, `_setMacro`, opcode constant `FEA_CMD_SET_MACRO`) writes up to
five 56-byte chunks with an explicit final-commit flag. These method pairs were
compared in full across the installers as recorded above.

The vendor implementation counts nonzero chunks instead of finding the final
nonzero chunk. That loses sparse trailing data and sends no packet for an
entirely empty slot. Linux always writes all five chunks, with commit set only
on chunk four, zero-padding its final 24 bytes. It then reads all four pages
without the vendor's early zero-page exit and compares the complete 256-byte
slot. This supports shortening or clearing a macro without intentionally
retaining its previous tail. A transfer failure can leave device state changed;
this is verified readback, not rollback.

Macro event encoding uses the existing [macro format](macros.md): repeat count,
keyboard events, mouse buttons and explicit-delay mouse movement. The CLI's
`macro`, `get-macro` (including `--decoded`) and `bind-macro` commands are enabled
for both migrated YC3121 models. Fn macro binding remains unavailable.

```sh
epomaker --device /dev/hidrawN macro 7 macro.json
epomaker --device /dev/hidrawN get-macro 7 --decoded
epomaker --device /dev/hidrawN bind-macro 9 7 --profile 1
```

## Custom RGB picture

RT100 and Dynatab75X-UK expose one writable custom picture at index 0. It contains
128 RGB triples (384 bytes), unlike the 126-slot (378-byte) picture layout used by
newer models. `get-picture`, `picture` and `picture-key` read, write and edit this
picture. A write sends seven 56-byte chunks, with the final chunk containing 48 data
bytes and eight zero bytes, waits 500 ms, then compares a complete readback. The
picture reader uses six `[8c, 0, page]` requests and expects 64 raw bytes from each.

The inherited vendor parent accepts a picture-bank argument but hardcodes bank 0.
Linux therefore rejects other picture indexes and makes no claim that the other
selectable lighting picture choices are editable. Picture writes are verified
readbacks, not rollback transactions; a failed transfer can leave earlier chunks
applied.

```sh
epomaker --device /dev/hidrawN get-picture 0
epomaker --device /dev/hidrawN picture 0 colors.json --activate
epomaker --device /dev/hidrawN picture-key 0 127 ff8040
```

## Main lighting

Both models select the same 21-effect catalog layout (`ce` on macOS, `ue` on
Windows; main-bundle lines 42554–42649). The complete layouts match after
renaming that alias. The mode table and encoder/decoder are in CommonKbYc500;
`MAXSPEED = 5` comes from its older keyboard parent. The newer YC3123 base uses
4, so its unmodified light encoder is unsuitable here.

`07` writes the light state with a checksum at byte 8, covering bytes 0–7;
`87` reads it back. Byte 1 is the effect, byte 2 is **5 minus the UI speed**,
byte 3 is brightness 0–4, byte 4 packs option and color flags, and bytes 5–7
contain RGB. The color flags and white substitution match the existing codec:
normal 7, rainbow 8, pure white sent as `fa ff fa`. Picture selection sends
RGB `00 c8 c8`. Writes wait the vendor's explicit 1000 ms before readback.

The backend accepts all 21 exposed modes, with these option limits: wave 0–3;
snake, kaleidoscope, line-wave and circle-wave 0–1; picture and music 0–2;
all others zero. Speed is 0–4 for animated effects; solid, picture, music and
screen have no speed control and require zero. Brightness zero provides the
vendor's way to turn illumination off. There is no explicit off effect and
neither model has side lights.

```sh
epomaker --device /dev/hidrawN get-light
epomaker --device /dev/hidrawN light wave --speed 4 --option 3 --rainbow
epomaker --device /dev/hidrawN light solid --rgb ff8040
epomaker --device /dev/hidrawN light picture --option 2
```

Selecting the existing picture choices is supported, and index 0 can be uploaded
through the custom RGB picture commands above. Selecting music or screen-following mode does not provide
background audio capture or screen-color streaming. Unknown effect IDs in
readback retain the raw packet and report `mode: unknown`.

## Remaining migration

Fn layers, display, manual OS controls,
configuration snapshots, reset, magnetic models, firmware, wireless routing,
and the GUI remain incomplete for this family. Macro recording and physical
playback validation also remain unfinished. CommonKbYc500 uses macro write `16`;
the newer driver's `0b` opcode must not be sent to this family. The CLI rejects unavailable commands before sending
them. Normal and older backends are separate classes to prevent opcode
collisions (for example, newer sleep `11` is older debounce).

[tests/test_yc3121.py](../tests/test_yc3121.py) exercises actual USB report
wrapping against an independently authored firmware simulator, profile and slot
isolation, settings offsets, limits, malformed responses, failed readback and
CLI selection. These tests validate the implementation against reconstructed
protocol facts; they are not hardware captures or a feature-parity score.
