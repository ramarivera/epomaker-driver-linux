# Glyph host-driven lighting audit

This audit covers the extracted Windows and macOS EPOMAKER Driver v4 bundles.
No network, firmware download, HID write, or hardware operation was attempted.
Offsets are raw UTF-8 byte offsets obtained with
`Path.read_bytes().find(...)`.

## Glyph reachability and device capability gate

The catalog entry at main-bundle byte **896116** (`id:3059`) identifies
Epomaker Glyph, VID 12625, PID 20482, keyboard type, and `other.isYC3123:true`.
Its `lightLayout:Ur` points to the layout object beginning at byte **570281**.
That object advertises RGB lighting and includes `LightMusicFollow2` and
`LightScreenColor` among the supported effect types. The effect catalog strings
are also present in the main bundle at bytes **154925** and **154854**.

The YC3123 controller's `supportsLightSync` method begins at byte **38315** in
both controller chunks. It returns false unless `deviceType.connect === "usb"`;
for USB it sends `commonMsg(new Uint8Array([143]), Bit7)` and returns true only
when the response exists, starts with command 143, and has response byte 11 set.
The host UI filters its live-sync device list to online keyboard devices whose
runtime `deviceType.supportsLightSync` is true. It then requires a resolved
controller object with a callable `sendSyncColor` method before starting updates.
Thus Glyph is reachable through this path only after USB runtime capability
probing succeeds; catalog support alone does not enable Bluetooth or 2.4 GHz
live updates.

## Effect-selection packet versus host live-sync stream

The normal YC3123 effect setter is `setLightSetting` around controller byte
**10724**. It sends the LED parameter report whose command constant
`FEA_CMD_SET_LEDPARAM` begins at byte **2224**. The effect map assigns
`LightMusicFollow2` numeric ID 22 and `LightScreenColor` numeric ID 21. For
music-follow modes it encodes `option << 4` plus the normal/dazzle flag; for
screen color it forces the option byte to zero. This selects the device effect;
it is separate from the host stream below.

`sendSyncColor` begins at controller byte **37979**. For an RGB array it builds
an 8-byte report header:

- byte 0: `15`;
- byte 1: `1`;
- byte 2: zero-based chunk index;
- byte 3: `56`;
- byte 4: `1` only on the final chunk, otherwise `0`; and
- bytes 5–6: zero padding before the RGB payload; and
- byte 7: the `Bit7` report checksum, generated by the shared packet wrapper.

It slices the RGB array into 56-byte chunks, pads the final chunk to 56 bytes,
and sends each 64-byte report with the shared `Bit7` report mode. There is no
layout inference in this method: it transmits the caller's RGB sequence as-is.

## Host processing and cadence

The host light-sync UI/plugin is in `57cfa1b3.js`. Its painter class begins at
byte **38401**. It allocates a 21×6 output canvas and updates the flattened RGB
output at byte **41508**. The per-device dispatch begins around byte **48063**:

- mode `rhythm` calls `painter.update(async outputs =>
  controller.sendSyncColor(outputs))`;
- mode `screen` calls `painter.updateScreen(async outputs =>
  controller.sendSyncColor(outputs))`; and
- `not-selected`, missing controller, or missing `supportSendSyncColor` stops
  the painter.

Both update loops schedule the next frame with an 8 ms timeout after the
previous send completes. This is a scheduling interval, not a 125 Hz wire-rate
guarantee: each send awaits the shared transport and its normal USB pacing.
The host can generate repeated HID reports independently of the device's
stored lighting effect. The screen painter source is a host plugin stream: it
uses a 21×6 thumbnail buffer and starts screen thumbnail capture through the
host plugin. The rhythm path uses the host plugin's configured audio analysis
(`numBands:32`, `fftSize:512`, gain/tilt/contrast/release/minDb/maxDb and attack
frames). Windows byte 47172 begins `numBands:32`, followed at 47184 by
`fftSize:512`, in the fallback configuration after `getConfiguration`.
No browser `getUserMedia`, `AudioContext`, or `AnalyserNode` string was found in
the inspected bundle path. The evidence points to the vendor host plugin
(`startPluginIfNotStarted`, `getConfiguration`, `startPluginIfNotStarted`) for
capture and analysis, not a browser-local media implementation.

The host surface starts/stops its rhythm and screen plugins on mount/unmount;
stopping clears painter timers and destroys painters. At Windows byte 46908 the mount effect assigns
`G.light.lightType="LightAlwaysOn"` when the current type is music-follow-2 or
screen color. This is an observed model-state assignment, not by itself proof
of a separate required wire-level reset. Linux explicitly applies solid lighting
for those two types and restores the saved raw settings on explicit stop.

## Screen path and RGB dimensions

The host screen stream uses a 21×6 thumbnail grid. The painter's output is a
flat RGB array with three bytes per grid cell, so the observed screen stream is
378 RGB bytes per frame before the controller chunks it into seven 56-byte
payloads (the final chunk is padded). The controller code does not assert that
this is Glyph's physical key or screen geometry; it only sends the host layout.
The Glyph catalog's 428×142 screen metadata is therefore not evidence that the
host live-light grid maps to the Glyph screen. It is a separate catalog field.

The rhythm painter uses the same 21×6 output contract after its configurable
canvas/layout processing. The source exposes layout controls in the host UI,
but this audit does not infer a physical key-to-pixel mapping from those
controls.

## Boundaries and actionable Linux implication

The extracted vendor path establishes a concrete Glyph live-light transport:
USB capability query → host rhythm/screen frame generation → 21×6 RGB output →
64-byte reports with command prefix `[15,1]` and 56-byte chunks. It does not
establish a Linux audio/screen capture implementation, a Glyph-specific physical
pixel layout, or a required autonomous effect selection sequence.

A Linux implementation should keep these as separate concerns: expose a USB
capability probe for response byte 11, preserve a caller-supplied RGB layout,
chunk exactly as observed, and treat audio/screen capture and layout editing as
remaining workflows to implement separately. Do not claim parity with the vendor's capture
plugin or infer Glyph screen geometry from the 21×6 host canvas.
