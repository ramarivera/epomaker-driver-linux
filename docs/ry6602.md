# RY6602 core configuration

Five EPOMAKER models now have CLI/backend core support. Their catalog entries are
marked `ry6602-core`, and all remain hardware-unverified.

| Model | Internal ID | Normal profiles | macOS model chunk | Windows model chunk |
| --- | --- | --- | --- | --- |
| SN020 | 3858 | 4 | `046e350b.js` | `2cccc7dc.js` |
| Epomaker EK75 | 3633 | 3 | `dc81b545.js` | `d56d2758.js` |
| TH80 V3 MAX | 3673 | 3 | `e056703d.js` | `1776c04e.js` |
| TH80 V2 | 3573 | 3 | `62aa4e65.js` | `dbdbff14.js` |
| TH65 Max | 3674 | 3 | `d2fa8818.js` | `6e41095e.js` |

Enabled operations are identity/status, normal and Windows/Mac Fn keymaps,
physical-slot remapping, macros, profile selection, sleep timers, debounce, OS options,
main lighting, model-specific side lighting and five custom RGB pictures.
Each has one Fn layer per OS. Writes retain full readback checks, preserve
unrelated keyboard-option fields and reject out-of-range profiles before writes.

```sh
epomaker discover
epomaker --device /dev/hidrawN status
epomaker --device /dev/hidrawN key 9 00000500 --profile 2
epomaker --device /dev/hidrawN matrix --fn --os-mode 1
epomaker --device /dev/hidrawN debounce 10
epomaker --device /dev/hidrawN options --system mac
```

Full snapshots and reset with recovery are supported. Graphical controls remain
unimplemented for this family.
RGB24 still and animation uploads are supported on its three screen-equipped models. Unsupported operations fail
before writes, including mixed batches whose first command would be supported.
No firmware flashing or device pairing is enabled.

## Shared protocol evidence

All five macOS model chunks inherit `d90cb3c5.js`, which inherits the already
migrated `623d2d52.js`. Windows uses `c3a25c70.js` and `17dc9c62.js` respectively.
The RY6602 base changes only `upgrade` and `supportsLightSync`; it does not
override key/Fn/macro or OS-option methods. TH80 V2 and TH65 Max also override
lighting color constants, handled by model-specific encoding and decoding.
The other class members are default matrices.

Normal, Windows Fn and Mac Fn arrays match byte for byte between the two
installers for every model. Functional data is packaged under
`src/epomaker_driver/data/ry6602-<id>-matrices.json`; no vendor code is distributed.
The explicit model allowlist is `models.RY6602_IDS`.

## USB discovery

Both installers list vendor `3151`, product `5056`, usage page `ffff`, usage `2`,
interface number `2` as a keyboard command collection. macOS filter source is
`index.5af2e057.js`, original line 377, offsets 1094374–1094464; Windows is
`index.feaf50e4.js`, original line 374, offsets 1088933–1089023.

Linux discovery now accepts that product ID only when the descriptor has the
matching vendor collection, report ID zero and a 64-byte feature payload. The
shared protocol constructs 64-byte commands. Interface numbering is not used
as a substitute for descriptor validation. The opened node's VID/PID, bus and
complete descriptor are rechecked to detect stale discovery paths.

This is source-backed discovery support, not a captured RY6602 descriptor or
physical compatibility claim. Product `5058` is a separate mouse filter and is
not accepted by this change. Receiver discovery and additional Bluetooth IDs
are not enabled without their own descriptor/transport evidence.

## Remaining model differences

The sleep metadata lacks a receiver deep-sleep field for this family. SN020/EK75
have 600-second minimums, TH80 V3 MAX permits zero, and TH80 V2/TH65 Max use
10-second minimums. The three-timer setter preserves that missing control as described below.

Screens use RGB24: SN020 is 33×7 with 8 MiB, TH80 V3 MAX is 7×7 with 2 MiB, and
TH65 Max is 7×7 with a special 2352-byte allocation path. EK75 and TH80 V2 declare
no screen. Those formats and allocation rules are implemented as described below.

`tests/test_ry6602.py` runs all five models through a simulated USB feature-report
adapter, checks matrix/profile isolation, macros, Fn/OS behavior and operation
gates. Descriptor tests reject wrong usage, wrong report length and the mouse
product ID. These tests do not measure timing or persistence on hardware.


## Three exposed sleep timers

```sh
epomaker --device /dev/hidrawN get-sleep
epomaker --device /dev/hidrawN sleep 600 1200 1800
```

The arguments are Bluetooth backlight timeout, receiver backlight timeout and
deep Bluetooth sleep, in seconds. RY6602 rejects a fourth argument. Glyph, RT85
and RT75 continue to require four values. The read/status response for RY6602
contains only the three exposed fields.

| Models | Minimum for each exposed timer | Maximum |
| --- | --- | --- |
| SN020, EK75 | 600 seconds | 64800 seconds |
| TH80 V3 MAX | 0 seconds | 64800 seconds |
| TH80 V2, TH65 Max | 10 seconds | 64800 seconds |

The catalogs declare these fields through `sleepBT.sleep`, `sleepBT.deep` and
`sleep24.sleep`. There is no `sleep24.deep`. The UI's `support24gDeepSleep`
checks that property (macOS main pretty lines 111729–111734), while the inherited
protocol still reads/writes four little-endian uint16 values at bytes 8–15 using
`91`/`11` (shared `623d2d52.js`, lines 219–252).

The Linux setter holds one transport transaction while reading the existing
response, preserving bytes 14–15, writing the three validated values and reading
back all four fields. The preserved field is opaque; even values above the
user-facing maximum are retained byte for byte. A missing/malformed initial
response prevents any write. A changed hidden field or mismatched exposed timer
fails the readback check. Only then are the three exposed values returned.

The checksum covers the first seven bytes, so carrying bytes 14–15 into the
new timer packet does not require changing the checksum. These semantics have
simulated USB tests on every migrated RY6602 model; timing and persistence on
physical devices remain unverified.


## Lighting modes and color flags

All five models use main layout `S`: 21 effects, with no explicit `LightOff`.
Set brightness to zero to darken a main effect. SN020 and EK75 have no side strip.
TH80 V3 MAX, TH80 V2 and TH65 Max use side layout `op` on macOS (`np` on Windows):
wave, snake, breathing and off, with maximum speed 3. Unsupported side requests
fail before writing. Those side definitions match after accounting for the
minified symbol rename (macOS main pretty lines 43432–43440).

| Models | Normal flag | Rainbow flag |
| --- | --- | --- |
| SN020, EK75, TH80 V3 MAX | 7 | 8 |
| TH80 V2, TH65 Max | 8 | 7 |

The flag changes apply to ordinary main/side effects. Music uses 0/4, picture
uses the bank index in the high nibble, and screen-color mode uses zero, as in
the inherited protocol. Those special cases must not be swapped indiscriminately.

TH80 V2 and TH65 Max also override `COMMONCOLOR`, so preset indices 0–6 decode
with different palettes. The model-specific flags and palettes match byte for
byte across their macOS and Windows class definitions. They are represented in
`models.light_encoding` and used for both writing and interpreting readback.
The raw response remains available alongside decoded values.

```sh
epomaker --device /dev/hidrawN light wave --rainbow --speed 3
epomaker --device /dev/hidrawN light solid --rgb ff8040
epomaker --device /dev/hidrawN light solid --brightness 0
# Only TH80 V3 MAX, TH80 V2 and TH65 Max:
epomaker --device /dev/hidrawN light breathing --side --rainbow
epomaker --device /dev/hidrawN get-picture 4
```

The five custom RGB banks use the shared 378-byte writer/readback and per-slot
editing. Lighting writes compare the actual mode, speed, brightness, flags and
RGB bytes. These packet and palette tests are simulated; physical appearance,
firmware normalization and persistence remain unverified.


## RGB24 displays

| Model | Dimensions | Still banks | Maximum animation frames |
| --- | --- | --- | --- |
| SN020 | 33×7 | 5 | 255 |
| TH80 V3 MAX | 7×7 | 5 | 255 |
| TH65 Max | 7×7 | 5 | 16 |

EK75 and TH80 V2 declare no screen and reject display uploads. The three screen
models have no clock/language/system-information flags; those commands remain
unavailable even though the shared base can encode them.

`screen` and `animation` automatically select RGB24 based on the identified model.
Pixels are column-major, with three bytes per pixel in R,G,B order. Alpha is
composited onto black. `--fit` preserves aspect ratio and adds black borders.
The Python media helpers accept the same model IDs.

```sh
epomaker --device /dev/hidrawN screen led-image.png --fit --bank 5
epomaker --device /dev/hidrawN animation led-animation.gif --fit --delay-ms 80
```

The inherited `getTFTLCDDataRGBImg` and `setTFTLCDDataRGBImg` methods select `a9`
and `29` for RGB24, versus `a5` and `25` for RGB565. Headers, 56-byte chunks,
checksums, retry limits and per-frame chunk-index resets remain the same. The
preparation command is a write handshake, not pixel readback. Source: macOS
`623d2d52.js`, lines 314–366; Windows counterpart `17dc9c62.js`.

The converter sorts by x then y and emits R,G,B bytes for mode `24` (macOS main
pretty lines 13490–13516). SN020 and TH80 V3 MAX use the standard 4-KiB block
allocation plus a 4-KiB header and five still reservations; their computed frame
counts exceed the application's 255-frame cap. TH65 Max takes a special path:
`floor(2352 / (7*7*3)) = 16`, with `memorySize` interpreted as bytes. This is the
explicit ID-3674 branch in `maxFrameCount` (main pretty lines 110149–110166).

Tests check RGB ordering, alpha, real media conversion, full packet payload
reconstruction, fifth-bank headers, animation limits and CLI selection for all
three models. Completion means packets were sent; no pixel readback, visual
hardware comparison or firmware-persistence verification is implemented.


## Recovery and factory reset

RY6602 backups use schema version 5. They contain all normal profiles, actual
Windows/Mac Fn maps, referenced macros, five RGB picture banks, raw lighting
settings, debounce, OS options and exactly three exposed sleep values. SN020
and EK75 use `side_light: null`; the other three models retain their side settings.
All encoded lighting bytes are preserved, including their different color flags.

```sh
epomaker --device /dev/hidrawN backup saved.json
epomaker --device /dev/hidrawN restore saved.json --backup before-restore.json
epomaker --device /dev/hidrawN factory-reset --backup before-reset.json
```

Restore validates the model, profiles, side-light capabilities and timer limits
before mutation. It rejects a fourth timer field rather than allowing a snapshot
to write an unexposed setting. The current hidden field is preserved by the
three-timer setter; it is not restored from the snapshot. This limitation is
recorded in backup, restore and reset results. Screen pixels remain outside backups.

The reset command is the inherited YC3123 `01` operation. Before sending it,
the driver saves and validates current settings and **all 256 macro slots** in a
new private recovery file. Reset can change the hidden field to a factory value;
subsequent restoration retains that current value rather than claiming to recover
unknown firmware state. A successful send is not verification of factory defaults.

Every migrated model has simulated USB tests for capture/restore, hidden-field
preservation, malformed input, side capability validation, cross-model rejection
and recovery-file existence before reset. Physical behavior remains unverified.
