# RT75 core configuration

RT75 (internal ID 3223, `yc3123_kf110_3m_1k`) has an initial CLI/backend
implementation, marked `rt75-core` in the catalog. It is not hardware-verified.

Enabled operations are identification, restricted status, three normal profiles
(indices 0–2), Windows/Mac Fn matrices, four-byte key bindings, 256-byte macro
slots, sleep timers, debounce and OS options. Configuration writes retain the
existing readback checks. Sleep bounds come from the model metadata: all four
timers must be 60–3600 seconds. The debounce protocol uses a single unsigned byte;
the catalog declares the control with `deBounce: 10`. This declaration is not
assumed to establish a hardware-verified debounce maximum.

```sh
epomaker --device /dev/hidrawN profile 2
epomaker --device /dev/hidrawN key 9 00000500 --profile 2
epomaker --device /dev/hidrawN matrix --fn --os-mode 1
epomaker --device /dev/hidrawN sleep 60 120 600 1200
epomaker --device /dev/hidrawN debounce 10
epomaker --device /dev/hidrawN options --system mac
```

Lighting, display, full snapshots, reset and the graphical interface remain
unavailable for RT75. Its catalog has a different main-light layout (`S`), no
side-light layout, and a 240×240 RGB565 screen without an explicit still-bank list.
These differences must be resolved before extending those operations. The
existing Glyph/RT85 snapshot schemas reject RT75 rather than silently omitting
unsupported state.

## Installer evidence

| Source | Model class | YC3123 parent | Shared keyboard base |
| --- | --- | --- | --- |
| macOS | `a3332e6a.js` | `2cea305b.js` | `623d2d52.js` |
| Windows | `9d912820.js` | `c6c9152c.js` | `17dc9c62.js` |

These paths are under `app/dist/js`. Both model classes contain only three
matrix fields and inherit the same transport methods used by Glyph and RT85.
All three class arrays match byte for byte between the installers, as does the
shared base's initial matrix. Functional arrays are packaged in
`src/epomaker_driver/data/rt75-matrices.json`; vendor program code is not included.
The catalogs also agree on model capabilities and timer bounds.

## Mac Fn default mismatch

The model defines `defaultFnMACMatrix` (uppercase `MAC`), but the shared base
reads `defaultFnMacMatrix`. The base initializes the latter to its generic `Z`
matrix. Its `setFnKeyConfigSimple` selects that inherited field when restoring
a default Mac action. This is visible in the macOS shared protocol at lines
1641–1677 and the corresponding Windows base. The different capitalization
appears in both model bundles.

The data file preserves both names: `defaultFnMACMatrix` is the model's declared
array; `defaultFnMacMatrix` records the effective inherited fallback. This records
vendor behavior and does not claim either array is the intended RT75 firmware
factory state. No automatic rewrite or default-reset action is added.

Reading Fn configuration (`90`) uses the explicit OS selector and page index,
independently of these default arrays. Linux writes explicit physical slots
(`10`) and verifies the actual matrix. Tests exercise both OS layers, preserve
the other layer and restore the previously read bytes; they do not substitute
the questionable vendor default array for device state.
